# One learning task and the wider plan

## Key takeaway

Use one meaningful, observable current task while retaining revisable subject and goal maps when they are useful.

## Summary

This reader guide combines the one-task-at-a-time convention and the optional two-level learning-plan record instructions. It distinguishes the current task, panorama, goal concept map, proposed learning episodes and actual observations. No fixed task duration, planning software, or validated mastery score is required.

## One continuing programme without document switching

The [master Practice](../practices/ai-assisted-learning-orchestration.md) puts the full procedure in one file. Define the overall target, identify provisional learning stages, select one current task, teach or ask for retrieval, wait for the real reply, assess against an inspectable criterion and choose the next action. Preserve actual attempts separately from plan revisions, and resume from the current decision instead of restarting the whole procedure.

**Overall target → learning stage → task → attempt** is a learner-specific hierarchy. The master’s Stage1–Stage7 headings describe its reusable procedure, not seven mandatory subject modules. Day labels remain scheduling choices. You may stay in the master; this guide and the specialist Practices provide optional record detail and alternative entry points, not required prerequisites.

## Default adaptive roadmap for a new subject

The self-contained master Practice supplies the actual steps; this optional guide summarizes its initial handoff. Do **not** start with a detailed multiweek list of daily questions.

| Step | What the learner and coach decide | Keep distinct |
|---|---|---|
| 1. Learner starting point | Short self-report on goals, prior experience and constraints; optionally one checked response collected **before instruction** | Self-reported confidence versus observed competence; unknown is not failed |
| 2. Subject areas or subsystems | A compact, source-grounded panorama: each candidate area's central question, boundary, an example and important overlaps | Academic explanatory perspectives versus arbitrary syllabus chapters |
| 3. High-level stages | A few provisional capabilities, combining areas as useful, with candidate checkpoints and reasoned prerequisites | Subject-map relationships versus instructional prerequisites |
| 4. One active task | Only the first meaningful, answerable activity with expected response, checked criterion, permitted help and stop/split rule | Day labels versus stable learning-task identities |
| 5. Evidence-led adaptation | Preserve original answer, actual help and criterion-based feedback; choose one next action | Task success versus independent stage-level or retained learning |

For English, a panorama might distinguish phonetics, phonology, syntax, semantics and pragmatics by their explanatory questions, while recognizing the cross-cutting role of prosody. A learner's proposed stage could combine syntax and semantics to explain one sentence; there is no one-to-one rule assigning each linguistic area its own week. Show the roadmap for orientation, then work on **one** task. Keep future task details undecided until the learner responds and the evidence is interpreted.

## One task at a time

Begin with one meaningful learning task and a real check; expand only when the task or evidence calls for it.

## Find the next task

1. **Locate the goal.** For a new subject, use a brief panoramic orientation and a goal-specific concept map to locate one meaningful capability; reuse an existing checked map if available. For a well-defined small question, begin directly and backfill the map only if it helps. The panorama is context, not a compulsory preliminary study session.
2. **Choose one observable output.** Ask what the learner can explain, solve, compare, identify or demonstrate at the end. Prefer one relevant relationship or decision to isolated trivia. If the task requires several distinct capabilities that are not yet available, select a first useful part rather than making a miniature syllabus.
3. **State the task boundary.** Agree on the input or reference, response to produce, permissible answer assistance and access supports, criterion for checking, and conditions for stopping or splitting. A deadline or time box is optional and locally chosen, not an empirically guaranteed optimal duration.
4. **Attempt before feedback when appropriate.** Keep the original response and the actual assistance. A full explanation or worked example is legitimate when prerequisites are absent or the learner requests it, but it is not an independent attempt.
5. **Check and decide once.** Compare the response with a credible criterion. Choose *continue*, *revisit*, *split*, *increase the challenge*, *defer*, or *stop*, and note the reason. Never mark delayed retention or transfer as observed merely because the next task is planned.

## A usable one task card

| Field | What to write |
|---|---|
| Goal and location | What larger capability and map region this task serves, if known |
| Next task | One concrete question or action within a defined, authorized scope |
| Observable output | The response, explanation or artifact the learner will produce |
| Checking criterion | What evidence would support or challenge success on **this** task |
| Assistance boundary | Allowed tools, answer hints, source access and accommodations |
| Stop or split rule | When to check, clarify, break down, defer or end the task |
| Record link | Optional private plan version, learning-stage ID and task ID |

For a single small task without a formal curriculum, only the task, output, criterion, assistance boundary and next decision are necessary. The JSON planning record is optional; a private note is sufficient.

## Constructed first day examples

**Introductory machine learning.** Given a checked introductory definition and a constructed example of training and test data, explain in your own words why low training error does not guarantee good performance on unseen data. **Output:** one explanation and a contrasting counterexample. **Criterion:** separate observed training performance from generalization, noting that unseen data may differ. **Next:** check one misunderstanding or choose a new application; do not infer broad ML mastery.

**Authorized security laboratory.** Given a lab host explicitly within your permission and one already collected service observation, identify what the observation shows, what it does *not* establish, and **one justified next investigation question**. **Output:** a short observation–hypothesis–question record. **Criterion:** the conclusion follows from evidence rather than an assumed vulnerability. **Next:** revisit service fundamentals or select a different scoped observation. Do not invent scanning results or provide an exploitation chain. Follow the lab provider's rules for AI assistance; do not use AI where an examination prohibits it. "Day 1" is an example label, not a universal curriculum duration.

Both examples are invented instructional designs, not completed learner results or evaluated AI interventions.

## Connect the five Practices

- [Concept Mapping and Instructional Sequencing](../practices/concept-mapping-and-instructional-sequencing-with-ai.md) chooses the next task **from** a tentative staged plan; it owns revisions to that plan.
- [Self-Regulated Learning](../practices/self-regulated-learning-with-ai.md) carries out the current task and preserves the learner's actual response.
- [Formative Assessment](../practices/formative-assessment-with-ai.md) investigates **one** observed discrepancy and proposes a justified adjustment.
- [Retrieval and Distributed Practice](../practices/retrieval-and-distributed-practice-with-ai.md) conducts a bounded recall task and separately plans later review.
- [Evaluation](../practices/evaluation-of-ai-assisted-learning.md) interprets a **specified** learning claim without converting one success into a mastery certificate.

Do not require all five for every task. No AI prompt by itself produces persistent memory, automatic reminders, source verification, correct grading or learner agreement.

## Use and evidence limits

These steps are KPS-specific design choices informed by the existing academically source-aligned library, not findings that every learner or subject benefits from identical task sizes. More substantial integration tasks are sometimes needed to assess relationships across topics. Task completion and independent, delayed learning remain distinct. Store actual records privately; do not publish learner data or fabricate observations.

## Optional two level learning plan

A plain private table is sufficient; the structured JSON schema is optional and cannot certify learning.

## Begin with the three artifacts

| Artifact | Minimum useful information | Does not establish |
|---|---|---|
| Subject panorama | Boundary, major regions, purposes, selected relations, source limits and omissions | Complete disciplinary coverage or understanding |
| Goal concept map | One focus question, selected concepts, explicit propositions and links back to the panorama | Which concept must be learned first |
| Adaptive stage plan | Capability, concepts, activity, proposed prerequisites, allowed assistance, check, criterion and revision trigger | An observed learning outcome or universal progression |

The prerequisite register is a set of task-sensitive hypotheses, not a fourth knowledge level. Label a relation as required for this task, helpful, or corequisite only with a rationale and a way to probe it. Even a supported declaration must state the evidence and scope; the checker cannot verify it.

## Use the optional template

1. Copy [the blank template](../data/two-level-learning-plan-template.json) outside the public repository. Use `record_kind: template` while fields are intentionally empty; a template pass does not mean a usable plan exists.
2. Inspect [the constructed example](../data/two-level-learning-plan-example.json). It demonstrates syntax and hypothetical design only. No source review, learner agreement or performance is invented by the example.
3. Fill the panorama before zooming to the goal map. Existing checked panoramas can be reused; keep the versions and scope visible. Select `proposed_plan` when the records contain a usable proposal, or `constructed_example` for explicitly invented demonstration data.
4. Use stable region, concept and learning-stage IDs. `order` is a replaceable display position, not the stage identity or proof of developmental necessity. A stage ID such as `normalize` remains unchanged when reordered. This differs from the repository Practice's navigable StageN headings.
5. Keep the learner's actual response in a separate [session record](SESSION-RECORDS.md). Refer to it privately in the prerequisite evidence or revision history rather than copying it into the public knowledge base.

## Choose one current task

A learning plan can contain several provisional stages while presenting **one next task** for immediate work. Use the optional `next_task` object to specify an `id`, `stage_id`, `task`, `observable_output`, `criterion`, `allowed_resources`, `assistance_boundary` and `stop_rule`. This is a proposed activity, not a learner response or a validated progression. `null` means no next task is selected yet; prior plans without this optional field remain readable by the checker. The ID references a stable learning-stage ID, not the navigable `StageN` headings of a KPS Practice. A day label is optional and never a performance claim.

Choose the smallest *meaningful* evidence-producing action, not the smallest dictionary fragment. If important relationships need to be applied together, the next task may be integrative. A ready learner may bypass redundant preliminary episodes with supporting evidence. See [the one-task steps](#find-the-next-task); retain the original map, plan and revision history rather than overwriting earlier decisions.

## Field interpretation

`sources` records citations, locators and inspected/uninspected/constructed status. Source references on nodes or propositions support the content declaration, not learner competence. `source_supported` requires a declared inspected source; a source declaration does not prove that inspection occurred.

`panorama.regions` supplies the broad view, while `goal.panorama_region_ids` and `goal_map.concepts[].panorama_region_ids` preserve the zoom relationship. `goal_map.relations` stores source concept, linking phrase and target concept. Nodes alone are not the intended concept map. Source-supported, unverified and constructed propositions remain distinguishable.

`prerequisite_hypotheses` names concepts, kind, proposed/supported/rejected status, rationale, probe and evidence references. Unsupported hypotheses may remain proposed. Rejected prerequisites cannot remain in a stage's prerequisite list. Evidence references are descriptions of private records, not files the checker uploads or opens.

`learning_stages` provides target capability, concepts, activities, allowed instructional help, a separately specified check and an adaptation trigger. `next_task` selects at most one current proposed task from those stages; it never stores an observed answer. `requires_stage_ids` is reserved for a chosen required-before ordering of learning episodes. It needs its own rationale and may be revised; conceptual map edges are never converted automatically to stage dependencies. Related concepts may form cycles, but contradictory strict stage ordering must be repaired or combined into a corequisite episode.

`learner_agreement` remains `not_recorded` until actual agreement exists. `agreed` needs `agreement_evidence`; neither the assistant nor a test should fabricate it. `revision_log` states versions, affected stage IDs, the change and reason. A source correction or learner choice can justify a revision without inventing a performance result; a performance-based revision requires an actual observation reference. Retired or split stage IDs stay in the history instead of being repurposed.

## Adaptation from evidence

| Observation or choice | Planning response |
|---|---|
| Prior capability is demonstrated appropriately | Consider omitting redundant teaching; retain the observation |
| A relationship cannot be explained or used | Add a relational example or integration task |
| An answer is correct only after help | Record assistance and plan a new independent check |
| A required-before hypothesis is contradicted | Revise that hypothesis and the stages that relied on it |
| A source or map claim is erroneous | Correct the representation before interpreting learner performance |
| Goal, workload or interest changes | Re-scope or defer with learner agreement, not an invented failure |

A learner can pause, request a direct explanation or decline a check. There is no universally required number of regions, concepts, stages, attempts or minutes. Later retention and changed-context checks remain planned until actually performed.

## Read only checks

```bash
python3 tools/check_learning_plan.py data/two-level-learning-plan-template.json
python3 tools/check_learning_plan.py data/two-level-learning-plan-example.json
```

The checker validates the declared format, links between levels, proposition fields, references, prerequisites, stage ordering and revision declarations. It accepts conceptual cycles but rejects contradictory required-before stage cycles. It does not write, generate stages, fetch sources, inspect private referenced records, infer a learner state, schedule sessions or classify mastery. A successful check is structural only.

## Scientific and privacy boundaries

The source-aligned [Concept Map](../concepts/concept-map.md) and [Concept Mapping](../methods/concept-mapping.md) objects explain the scholarly representation and procedure. This record schema and the two-level coaching sequence are authored design choices. Preserve source limitations and keep private content outside public version control. These examples are constructed; no real learning results are stored here.
